HOW IT DECIDES

Deterministic checks. No model in the loop.

The agent proposes a trade. Code — never the model — computes every threshold and owns the send/block decision, in a fixed order, first failure wins.

DRAWDOWN_BREACH

Session drawdown halt

Halts once cumulative realized + unrealized P&L crosses a configured loss threshold for the session — regardless of how small each individual trade was.

VELOCITY_EXCEEDED

Trade-frequency cap

Halts when trade count in a rolling window exceeds a limit — the check no per-order validator can perform, since it depends on the ten trades before it.

LADDER_DETECTED

Loss-ladder detection

Flags a same-direction position increase after a loss on that symbol — the martingale pattern behind several of the largest account blowups on record.

DATA_UNAVAILABLE

Fail-closed on missing data

If market price or account state can't be read, fresh and sane, the next trade is blocked. No data, no trade — never a silent fallback to stale state.

ARCHITECTURE

Sits in front of Binance's own MCP server.

SessionGuard is a transparent MCP proxy. The agent connects to it exactly as it would connect to Binance directly — every call is either forwarded unmodified or blocked before it ever reaches Binance's own confirm-before-execute step.

FOR THE JUDGES

Questions judges ask.

Q1

Does this replace TradeGuard's per-trade checks?

No. Per-ticket size, leverage, and symbol validation is TradeGuard's layer. SessionGuard operates one level up, on the running session — cumulative drawdown, trade velocity, and loss-ladder patterns that a per-order validator structurally cannot see, because it evaluates one ticket at a time and holds no memory of the ten before it. TradeGuard's own README states it implements no velocity or drawdown circuit-breaking; SessionGuard is precisely that layer, and does not compete with per-ticket validation.

Q2

Does it touch live funds?

Not on the submission path. Per DECISIONS.md D-0, every scripted scenario runs against a deterministic MockUpstream, so the demo does not depend on live-market timing, token state, or Binance availability. A live Binance fill is attempted only after the entry is otherwise submittable, as an enhancement — never a blocker. There is no withdrawal scope to request in any case.

Q3

Why block a trade instead of resizing it to fit under the limit?

SessionGuard never proposes, sizes, or times a trade (protected property P-5) — resizing an order would mean the supervisor authoring one, which is exactly the boundary it holds. The model proposes; deterministic code decides forward or block. A halt is also meant to be read by a human: the audit log shows the exact sequence that crossed the line, and the operator tightens the config and re-arms.

SCOPE GUARANTEES

What SessionGuard never does.

The six protected properties in the PRD, and the no-withdrawal guarantee in SECURITY.md, stated as hard boundaries.

Never lets the model compute or report a halt. Every threshold comparison and every block code are deterministic TypeScript over config.json — no LLM output is ever the deciding number.

PRD §1.2 — P-1

Never resizes, re-times, or authors a trade of its own. It only forwards the agent's call unmodified, or blocks it and logs why.

PRD §1.2 — P-5

Never calls a withdrawal or external-transfer tool, and contains no code path that could. The restriction is grep-asserted in the test suite; the platform exposes no withdrawal scope to begin with.

SECURITY.md §5 — P-5

Never substitutes cached, stale, or assumed data for a failed read, and never places session state in the agent's context where a reasoning failure could mutate or erase it.
